PRD dan Blueprint Operasional
Aplikasi layanan pelanggan untuk toko online
Versi 2.0  |  28 Oktober 2026  |  Pemilik produk VELKIRA
Tujuan dan keputusan produk
Luma Support dirancang sebagai aplikasi kerja yang dapat digunakan petugas toko online untuk mencatat pertanyaan, mengelola keluhan, membagi tanggung jawab, dan memantau penyelesaian. Data disimpan di database, akses memerlukan login, dan setiap perubahan penting tercatat dalam riwayat.
Dokumen ini menetapkan kebutuhan sebelum pengembangan. Lingkupnya meliputi PRD, arsitektur server, database relasional, kontrak API, desain antarmuka, aturan proyek dan rencana implementasi. Checklist dipakai untuk mengarahkan pengerjaan; target kualitas masih harus dibuktikan melalui pengujian.
Cakupan rilis pertama
Rilis pertama dipakai satu toko dengan beberapa petugas. Petugas memasukkan permintaan yang diterima dari WhatsApp, marketplace, email, atau telepon. Aplikasi mengelola catatan, pemilik tiket, prioritas, catatan tindak lanjut dan status. Jawaban FAQ membantu petugas menyiapkan balasan berdasarkan kebijakan toko.
Koneksi WhatsApp dan marketplace tidak dianggap otomatis tersedia. Petugas tetap membalas melalui kanal asal sampai integrasi resmi diaktifkan pada fase berikutnya. Sistem tidak mengaku mengecek ekspedisi, mengirim pesan, atau memutuskan refund tanpa proses yang benar-benar terhubung.
Prinsip operasional
Data tetap tersedia setelah refresh, logout dan pergantian perangkat bagi pengguna yang berhak.
Statistik, daftar tiket dan riwayat berasal dari database dengan definisi metrik yang jelas.
Tidak ada tombol reset massal pada aplikasi produksi.
Akses publik portfolio hanya memperlihatkan studi kasus atau gambar yang telah disanitasi; workspace pelanggan memerlukan login.
Keputusan yang perlu dikunci sebelum rilis
Pemilik toko menetapkan kebijakan FAQ, jenis keluhan, target respons, aturan retensi, domain aplikasi serta akun hosting dan database. Rekomendasi arsitektur di dokumen ini menjadi dasar pengerjaan; biaya layanan diperiksa saat pengadaan.
Tahap 1 PRD dan KPI
Executive summary
Permintaan pelanggan sering tersebar di beberapa kanal. Tanpa catatan bersama, petugas kesulitan melihat masalah yang belum selesai, siapa penanggung jawabnya, dan tindakan terakhir. Luma memusatkan pekerjaan tersebut dalam tiket yang dapat dilacak.
Produk ditujukan untuk berbagai kategori toko online, termasuk pakaian, makanan kemasan, elektronik dan kebutuhan rumah. Pencatatan berfokus pada layanan pelanggan; pengelolaan penjualan, stok dan akuntansi tetap berada pada sistem toko masing-masing.

Mempercepat pencarian konteks pelanggan serta riwayat penanganan.

Alur masuk sampai penyelesaian
Pelanggan menghubungi toko melalui kanal yang digunakan. Petugas login, mencari pelanggan dan nomor pesanan, lalu mengecek apakah masalah yang sama sudah memiliki tiket terbuka. Jika belum, petugas membuat tiket dengan ringkasan, kategori, prioritas dan kanal asal.

Jika menunggu informasi pelanggan, status menjadi Menunggu Pelanggan. Jika perlu keputusan khusus, tiket dieskalasikan kepada admin.
Setelah masalah ditangani, petugas menulis ringkasan penyelesaian dan menandai Selesai. Jika pelanggan melapor bahwa masalah belum selesai, tiket dapat dibuka kembali dengan alasan; riwayat sebelumnya tetap utuh.
Contoh tiket yang realistis
Pelanggan Bima menghubungi toko terkait pesanan ORD 2402 yang belum sampai. Tiket mencatat waktu penerimaan, kanal WhatsApp, kategori pengiriman, prioritas normal, ringkasan keluhan dan referensi pesanan. Petugas yang mengambil tiket dicatat sebagai penanggung jawab.
Petugas memeriksa status pada sistem pengiriman yang digunakan toko, lalu mencatat hasil pemeriksaan serta pembaruan yang disampaikan kepada pelanggan. Pencatatan tindakan nyata dibedakan dari rencana yang belum dilakukan.
FAQ dan eskalasi
FAQ berisi kebijakan yang sudah diterbitkan admin. Petugas mencari dan menyalin jawaban; aplikasi mencatat penggunaan FAQ jika dipakai pada tiket. Jawaban ambigu tetap ditinjau manusia. Penggantian barang, refund dan janji kompensasi memerlukan keputusan sesuai kebijakan toko.

Standar performa dan aksesibilitas
Target awal beban: sampai 10 petugas serentak dan 10.000 tiket sebagai asumsi pengujian. Gunakan pagination 25 item, maksimal 100. Target p95 API baca 800 ms dan tulis 1.500 ms pada lingkungan uji yang dicatat, di luar gangguan provider. Kalibrasi target setelah pola penggunaan diketahui.
Antarmuka mobile dan desktop mendukung keyboard, fokus terlihat, label form, status berteks, kontras normal minimal 4,5 banding 1, dan target sentuh utama sekitar 44 px. Area kerja memakai noindex; halaman portfolio publik tidak memuat data pelanggan.
Keamanan dan pemulihan
Semua akses memakai HTTPS, validasi server, role dan pemeriksaan record. Data pribadi dibatasi sesuai kebutuhan. Tetapkan retensi dan prosedur penghapusan bersama pemilik toko. Target pemulihan awal: RPO 24 jam dan RTO 8 jam, dengan backup yang benar-benar tersedia serta uji restore; jangan menjanjikannya sebelum diverifikasi.

Pemisahan dari website agency
Website VELKIRA dapat tetap memakai static export. Aplikasi operasional Luma dibuat sebagai proyek server terpisah agar data privat, session dan API tidak tercampur dengan portfolio publik. Alamat support.velkira.site merupakan usulan subdomain; domain dan hosting ditetapkan saat persiapan rilis.
Alur request
Browser mengirim request terautentikasi ke API. Server memverifikasi session, status akun dan role, memvalidasi body, lalu menjalankan transaksi database. Respons sukses dikirim setelah commit. Statistik dibaca dari query yang terotorisasi, bukan dari perkiraan state frontend.
State dan caching
Database adalah sumber kebenaran. State browser hanya menyimpan filter, pagination dan draft. Setelah mutasi berhasil, muat ulang data terkait. Jangan cache bersama respons autentikasi, pelanggan atau tiket; gunakan private no-store pada endpoint privat. Aset berversi boleh di-cache. Jangan menyimpan token auth atau data pelanggan di URL.
Batas biaya
Anggaran mencakup hosting server, database, backup, SMTP dan monitoring. Integrasi channel atau AI memiliki biaya terpisah. Tidak menetapkan harga layanan dalam PRD; periksa kuota, lokasi data dan paket yang dipilih sebelum pembelian.

Session dan akses
Gunakan panduan SSR Auth sesuai versi SDK yang dipasang. Server memverifikasi identitas untuk setiap API; jangan mempercayai role dari form atau localStorage. Profil berisi role dan status aktif yang hanya dapat diubah melalui jalur admin. Public signup dinonaktifkan. Akun admin pertama dibuat melalui proses bootstrap terkontrol.
Key istimewa tidak dipakai untuk CRUD rutin karena dapat melewati RLS. Request biasa memakai identitas pengguna; mutasi melalui fungsi transaksi terotorisasi. Konfigurasi cookie, CSRF atau pemeriksaan origin mengikuti mekanisme session SDK yang dipilih dan diuji saat implementasi.

Indeks dan pencarian
Indeks tiket pada status, priority dan created_at; assigned_to, status dan created_at; customer_id; serta order_reference untuk pencarian referensi pesanan. Notes dan events diurutkan melalui indeks ticket_id, created_at. PK dan unique sudah memiliki indeks; hindari duplikasi. Mulai dari pencarian terstruktur, lalu tambahkan full text bila kebutuhan dan hasil query mendukung.
Batas DDL
Lampiran SQL menetapkan tipe, PK, FK dan constraint struktur. Sebelum produksi, migrasi wajib dilengkapi RLS policies, grant minimum dan fungsi transaksi untuk assignment, status, idempotency serta audit. DDL struktur saja bukan bukti database aman atau aplikasi siap rilis.

Aturan penyelesaian dan riwayat
Penutupan memerlukan owner aktif dan catatan resolution berisi tindakan serta hasil yang benar-benar dilakukan. Catatan internal tidak otomatis dikirim kepada pelanggan. Petugas mencatat balasan yang sudah dikirim pada kanal asal sebagai note jenis response dengan sent_at. Server memvalidasi received_at dan sent_at, lalu menetapkan first_response_at dari balasan pertama untuk KPI; waktu tidak boleh mendahului penerimaan atau berada di masa depan. Reopen menyimpan alasan, actor dan status sebelumnya; catatan lama tidak dihapus. Admin dapat memindahkan owner dengan alasan saat petugas tidak aktif.
Transaksi atomik
Assignment, perubahan status, versi dan event harus terjadi dalam satu transaksi. Claim memeriksa owner kosong dan versi terbaru. Update data memakai version yang dikirim pengguna; bila sudah berubah, server mengembalikan 409. Kegagalan penulisan event harus membatalkan perubahan tiket.
Pembuatan tiket dan catatan memakai request_id dari client. Database memiliki unique per actor dan request ID, serta request_hash SHA 256 dari payload awal yang dinormalisasi server; hash tidak diubah saat data tiket diperbarui. Retry dengan ID serta payload sama mengembalikan hasil sebelumnya; ID sama dengan payload berbeda ditolak sebagai konflik. Setelah timeout, client mencari hasil request sebelum mengulangi operasi.
Akses database
Aktifkan RLS pada seluruh tabel yang terekspos. Pengguna anonim tidak memiliki akses. Petugas aktif dapat membaca workspace, claim tiket kosong, dan memutasi tiket miliknya; admin menangani seluruh tiket serta pengaturan tim/FAQ. Semua mutasi melalui fungsi transaksi terotorisasi; akses tulis langsung ke tabel dicabut. Policies dan fungsi wajib diuji terhadap role, akun nonaktif serta upaya mengganti actor_id.
Retensi dan penghapusan
Tidak ada tombol hapus permanen tiket pada MVP. Penonaktifan akun dan pengarsipan FAQ menjaga histori. Retensi kontak, anonimisasi dan permintaan penghapusan diatur pemilik sesuai kebutuhan serta kewajiban yang berlaku; jangan mengklaim kepatuhan hanya dari desain ini.

Tahap 3 Payload dan response API
Membuat tiket
POST /api/v1/tickets
{
  "request_id": "uuid-dari-client",
  "customer_id": "uuid-pelanggan",
  "subject": "Pesanan belum sampai",
  "summary": "Estimasi terlewati dan perlu pemeriksaan",
  "category": "shipping",
  "channel": "whatsapp",
  "order_reference": "ORD-2402",
  "priority": "normal"
}
Server menetapkan creator dari session, status awal new, nomor tiket, version dan timestamps. Jangan menerima created_by, role atau actor_id dari browser. Subject 5–160 karakter; summary 5–4.000; channel dari daftar yang diizinkan; order reference maksimal 100. Tolak field tidak dikenal.
Menutup tiket
POST /api/v1/tickets/{id}/status
{
  "version": 4,
  "status": "resolved",
  "resolution": "Pelanggan menerima pembaruan dan masalah ditangani"
}
Catatan 5–4.000 karakter setelah trim. Endpoint resolution membuat note dan event serta memperbarui status dalam satu transaksi. Aktor harus owner aktif atau admin. Buka kembali menggunakan status in_progress serta reason; untuk operasi lain, validasi field yang memang diizinkan.

Typography dan layout
Gunakan Manrope untuk heading serta body dengan fallback Arial. H1 28–36 px, H2 18–24 px, isi 14–16 px dan label 12–13 px. Data pelanggan, catatan dan tindakan utama tidak boleh menggunakan ukuran caption. Spacing 4, 8, 12, 16, 24 dan 32 px. Radius panel 14–16 px dan tombol 8–10 px; shadow tipis.
Desktop dan mobile
Desktop memakai sidebar, header, metrik, filter dan daftar tiket. Detail memiliki ringkasan pelanggan/pesanan, catatan, status, owner dan riwayat. Mobile memakai daftar lalu detail, dengan tindakan utama tetap mudah dijangkau. Jangan menempatkan semua kolom tabel sebagai teks kecil pada ponsel.
State komponen
Form menyediakan default, fokus, validasi, saving, sukses dan gagal. Tombol saving dinonaktifkan selama request tanpa menghilangkan konteks. Tampilkan skeleton hanya ketika data benar-benar dimuat, empty state saat hasil kosong dan retry saat request gagal. Gunakan konfirmasi untuk tindakan berisiko seperti menonaktifkan petugas; jangan meminta konfirmasi untuk setiap simpan catatan biasa.

Angka kosong ditampilkan sebagai nol hanya jika query berhasil. Request gagal menampilkan keadaan tidak tersedia, bukan nol. Setelah simpan, tampilkan hasil dari server. Catatan internal diberi label yang membedakannya dari balasan pelanggan. Bila belum ada integrasi pengiriman, jangan menampilkan tombol Kirim yang seolah mengirim pesan.
Konflik dan pemulihan draft
Jika versi tiket berubah, tampilkan pesan bahwa data telah diperbarui petugas lain. Pertahankan draft dalam komponen selama layar masih terbuka; minta pengguna memuat ulang data sebelum mengulang simpan. Jangan menimpa data secara diam-diam. Peringatkan saat meninggalkan form yang belum tersimpan, tanpa menyimpan data pribadi otomatis ke localStorage.
Hubungan dengan portfolio
Halaman publik VELKIRA menampilkan studi kasus, fitur dan gambar yang telah disanitasi. Workspace operasional tidak dibuka anonim untuk pengunjung portfolio. Jika kelak diperlukan akun evaluasi, sediakan lingkungan terpisah dengan data yang aman dan izin terbatas; jangan menghubungkannya ke database pelanggan produksi.
Tahap 5 Project rules dan implementasi
Aturan proyek
Gunakan TypeScript strict pada proyek operasional baru dan validasi input di server.
Akses ditolak secara default; verifikasi session, akun aktif dan role setiap request.
Database adalah sumber kebenaran; jangan menampilkan sukses sebelum commit.
Semua perubahan tiket penting harus memiliki actor dan audit event.
Jangan mempercayai role, owner atau creator yang dikirim browser.
Gunakan transaksi, version dan request ID untuk mencegah overwrite/duplikasi.
Tidak ada seed pelanggan, password, API key atau data produksi di frontend.
Baca panduan versi framework dan SDK sebelum coding; hindari API usang.

Definition of done
Aplikasi operasional selesai ketika tiket tersimpan setelah refresh, otorisasi diterapkan, assignment atomik, catatan/resolution/audit konsisten, dan retry tidak menggandakan data. Pengujian peran dan akses ilegal wajib lulus. Temuan penting harus diperbaiki atau mendapat keputusan pemilik yang tercatat sebelum rilis.
Monitoring dan rollback
Pantau error API, kegagalan login, latensi dan koneksi database tanpa merekam isi keluhan atau kontak dalam log umum. Alert diarahkan kepada pengelola. Deploy dari commit teruji dan gunakan migrasi kompatibel. Rollback aplikasi tidak boleh menghapus transaksi pelanggan; pemulihan database dilakukan hanya melalui runbook yang telah diuji.
Keputusan sebelum go live
Konfirmasi akun layanan, biaya, kebijakan retensi, pemilik akses, prosedur eskalasi, target respons dan petugas penanggung jawab. Sediakan lingkungan staging terpisah. Integrasi WhatsApp atau marketplace baru dinyatakan aktif setelah kredensial, webhook, deduplikasi event, pengiriman serta recovery kegagalan lolos pengujian.
Lampiran SQL struktur identitas dan tiket
Spesifikasi PostgreSQL untuk Supabase. Jalankan hanya sebagai bagian migrasi yang sudah dilengkapi policies dan fungsi transaksi. Jangan memakai DDL ini sendirian untuk membuka akses produksi.
CREATE TABLE profiles (
  id uuid PRIMARY KEY REFERENCES auth.users(id),
  display_name text NOT NULL CHECK (length(trim(display_name))>0),
  role text NOT NULL CHECK (role IN ('admin','agent')),
  is_active boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE customers (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name text NOT NULL CHECK (length(trim(name)) BETWEEN 1 AND 160),
  contact_reference text CHECK (length(contact_reference)<=255),
  created_by uuid NOT NULL REFERENCES profiles(id),
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE tickets (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  number bigint GENERATED ALWAYS AS IDENTITY UNIQUE,
  customer_id uuid NOT NULL REFERENCES customers(id),
  subject text NOT NULL CHECK (length(trim(subject)) BETWEEN 5 AND 160),
  summary text NOT NULL CHECK (length(trim(summary)) BETWEEN 5 AND 4000),
  category text NOT NULL CHECK (category IN
    ('general','shipping','product','payment','return')),
  channel text NOT NULL CHECK (channel IN
    ('whatsapp','marketplace','email','phone','other')),
  order_reference text CHECK (length(order_reference)<=100),
  priority text NOT NULL CHECK (priority IN ('normal','high')),
  status text NOT NULL DEFAULT 'new' CHECK (status IN
    ('new','in_progress','waiting_customer','escalated','resolved')),
  assigned_to uuid REFERENCES profiles(id),
  created_by uuid NOT NULL REFERENCES profiles(id),
  request_id uuid NOT NULL,
  request_hash char(64) NOT NULL,
  version integer NOT NULL DEFAULT 1 CHECK (version>0),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  received_at timestamptz NOT NULL DEFAULT now(),
  first_response_at timestamptz,
  resolved_at timestamptz,
  UNIQUE (created_by,request_id),
  CHECK (status NOT IN ('in_progress','waiting_customer','resolved')
    OR assigned_to IS NOT NULL),
  CHECK ((status='resolved') = (resolved_at IS NOT NULL))
);
Default FK membatasi penghapusan record yang masih dirujuk. Timestamp penyelesaian wajib dihapus saat reopen melalui fungsi transaksi; riwayat lama tetap tersimpan dalam events.
Lampiran SQL catatan audit dan indeks
CREATE TABLE ticket_notes (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  ticket_id uuid NOT NULL REFERENCES tickets(id),
  author_id uuid NOT NULL REFERENCES profiles(id),
  body text NOT NULL CHECK (length(trim(body)) BETWEEN 5 AND 4000),
  kind text NOT NULL CHECK (kind IN ('internal','response','resolution')),
  sent_at timestamptz,
  request_id uuid NOT NULL,
  request_hash char(64) NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  CHECK ((kind='response') = (sent_at IS NOT NULL)),
  UNIQUE (author_id,request_id)
);
CREATE TABLE ticket_events (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  ticket_id uuid NOT NULL REFERENCES tickets(id),
  actor_id uuid NOT NULL REFERENCES profiles(id),
  event_type text NOT NULL,
  details jsonb NOT NULL DEFAULT '{}'::jsonb,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE faqs (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  question text NOT NULL CHECK (length(trim(question)) BETWEEN 5 AND 300),
  answer text NOT NULL CHECK (length(trim(answer)) BETWEEN 5 AND 4000),
  is_published boolean NOT NULL DEFAULT false,
  updated_by uuid NOT NULL REFERENCES profiles(id),
  updated_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX tickets_queue ON tickets(status,priority,created_at);
CREATE INDEX tickets_owner ON tickets(assigned_to,status,created_at);
CREATE INDEX tickets_customer ON tickets(customer_id);
CREATE INDEX tickets_order ON tickets(order_reference)
  WHERE order_reference IS NOT NULL;
CREATE INDEX notes_history ON ticket_notes(ticket_id,created_at);
CREATE INDEX events_history ON ticket_events(ticket_id,created_at);
